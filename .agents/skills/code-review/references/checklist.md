# レビューで問い直すこと

共通項目と対象言語の項目を、Codex 自身の調査に使う。全問をユーザーへ質問する手順ではない。
各問について「どの条件で失敗するか」「その条件に到達できるか」「コードやテストで何を確認したか」を考える。
該当する書き方を見つけただけで不具合と断定せず、バージョン、呼び出し契約、防御処理を確認する。

## 共通

- 空、null、0、負数、最大値、重複、不正入力ではどうなるか。境界の前後で仕様を満たすか。
- 外部入力はどこから来るか。認証に加えて対象データへの認可があるか。注入や秘密情報の流出に至る経路はあるか。
- 処理の途中で失敗したら、部分更新やリソースは残るか。例外を握り潰して成功として返さないか。
- 同時実行、再試行、キャンセル、順序の逆転で結果は変わるか。排他、冪等性、状態の整合性を何が保証するか。
- 入力件数が増えるとクエリ、I/O、メモリはどの程度増えるか。N+1 や無制限の蓄積が実際に起きるか。
- 既存の API、保存データ、設定、実行環境との互換性は保たれるか。移行・ロールバック時はどうなるか。
- 同じ責務の既存処理を探したか。今回の重複や抽象化が、具体的にどの不整合・修正漏れを生むか。
- 正常系だけでなく今回の失敗条件をテストしているか。そのテストは実装の写しではなく利用者に見える結果を検証するか。

## 運用・リリース（高リスク変更時）

- ローリングデプロイで新旧のアプリ、DB スキーマ、メッセージが共存しても契約は成立するか。
- 移行の途中失敗・再実行、ロールバック後に、新形式のデータを失ったり読めなくなったりしないか。
- 段階的リリースや Feature Flag の切り替え後、処理中のジョブや保存済み状態は整合するか。
- 障害や性能劣化を検出するログ・メトリクスがあり、原因の切り分けと復旧に使えるか。秘密情報を記録しないか。
- 外部サービス停止やタイムアウトで再試行が集中しないか。重複処理や部分更新から回復できるか。

## JavaScript / TypeScript・UI

- 型アサーションや型定義があっても、実行時の外部データは検証されるか。null や欠落した値を受け取る経路はあるか。
- Promise の失敗・待機・キャンセルは誰が扱うか。古い応答が新しい状態を上書きしないか。
- React の Hooks、Vue のリアクティビティなど、使用中のフレームワークの規則を満たすか。
- 購読やタイマーの解除、依存値、リストの識別子は適切か。再描画や並べ替えで状態が混ざらないか。
- キャッシュのキーに取得条件が含まれるか。更新失敗時や楽観的更新の巻き戻しで不整合が残らないか。

## Python

- 可変なデフォルト引数やクラス属性が、呼び出し間・インスタンス間で意図せず共有されないか。
- 広すぎる例外捕捉が障害を隠さないか。ファイル・接続は例外時にも解放されるか。
- async 関数内の同期 I/O がイベントループを止めないか。タスクの失敗とキャンセルを回収できるか。

## Go

- error や nil を受け取った経路はどうなるか。ラップ後も必要なエラー判定ができるか。
- goroutine と channel は成功・失敗・キャンセルの全経路で終了するか。context は適切に伝播するか。
- map や共有状態の同時アクセスを何が保護するか。defer による解放が長いループの終了まで遅れないか。
- ループ変数の捕捉を疑うなら、使用中の Go バージョンと変数の宣言位置で実際に問題が起きるか。

## Rust・C / C++

- Rust の unwrap、unsafe、共有状態に到達する入力と不変条件は何か。panic や未定義動作を防ぐ根拠はあるか。
- async の中断時にもロック・リソース・途中状態は安全か。ロック保持中の待機が停止を招かないか。
- C / C++ の所有権、寿命、境界、整数演算は有効か。二重解放や範囲外アクセスに至る経路はあるか。

## Java / Kotlin・データアクセス

- null、例外、トランザクション境界をまたぐと何が残るか。非同期処理の失敗は呼び出し元に伝わるか。
- スレッドや coroutine の終了、共有状態、キャンセルを誰が管理するか。接続やロックが残らないか。
- ORM の関連読み込みで N+1 が発生するか。SQL の値と識別子を安全に組み立て、データ単位の認可するか。

## Shell・設定・CI

- 空白や先頭のハイフンを含む値、未設定変数、失敗するコマンドでも意図した対象だけを操作するか。
- 引用、パイプの終了状態、再実行、途中失敗でデータ消失や誤った成功判定につながらないか。
- スキルや設定の配布対象を増減したとき、登録・有効化・検証・解除で扱う対象は一致するか。固定件数や別管理の一覧が更新漏れを起こさないか。
- CI の外部入力がシェルへ展開されないか。権限と秘密情報の利用範囲はジョブの目的に合っているか。
- CI の既定値やマトリクスの各組み合わせで、必須の検証が実行されるか。基準データや成果物が欠けたとき、検証をスキップしたままジョブが成功しないか。

他の言語でも、採用バージョンと既存の設計から同じ問いを立てる。
必要な仕様は公式資料で確かめ、別バージョンの規則をそのまま適用しない。
